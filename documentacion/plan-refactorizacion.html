Plan de Refactorización — Kaptas ERP Web API

Documento de Arquitectura · Cronograma Profesional · Asignación RACI

📅 Inicio: Lunes 13/07/2026 🏁 Fin estimado: Viernes 08/01/2027 👥 Equipo: 10 personas 📊 Duración: 26 semanas · 130 días hábiles 🔄 Versión: 1.0

1. ROL

Software Architect, Project Manager (PMP), Scrum Master y Technical Lead Senior con más de 20 años de experiencia en refactorización de ERP, CRM y sistemas empresariales de gran escala.

Enfoque: Este documento no contiene estimaciones superficiales. Cada tarea ha sido analizada contra el código fuente, la arquitectura real y las dependencias del proyecto Kaptas ERP Web API.

2. OBJETIVO

Refactorizar progresivamente Kaptas ERP Web API desde una arquitectura N-Tier monolítica legacy hacia una Arquitectura Limpia modular (v2) sin interrumpir las operaciones del sistema en producción.

Estrategia Híbrida

  • 🔵 Zona LEGADO: Código existente que NO se modifica — se protege con tests de caracterización.
  • 🟢 Zona PUENTE: Adaptadores que conectan el nuevo código con el legado durante la transición.
  • 🟡 Zona NUEVO (v2): Módulos refactorizados en Features/ con Clean Architecture.
  • ⚪ Zona LIMPIO: Módulos completamente migrados, legado eliminado.

3.4 Resumen Ejecutivo

Proyecto: Kaptas ERP Web API — Sistema multi-tenant para facturación electrónica (DGII/ECF), inventario, contabilidad, nómina, logística y restaurante en República Dominicana.

Tamaño: ~7 proyectos, ~233 entidades, ~60 controladores, ~100 servicios, ~1000+ endpoints

Riesgo principal: Ausencia total de tests fuera del módulo RepairShop (riesgo de regresión crítico)

Enfoque: Refactorización aditiva (no destructiva) — el código legacy permanece intacto mientras se construyen los módulos v2 en Features/. Cada módulo legacy se protege con tests de caracterización antes de migrar.

Duración estimada: 26 semanas (130 días hábiles) con equipo de 10 personas

Recomendaciones

  1. Feature Flags obligatorios: Cada módulo v2 debe poder activarse/desactivarse individualmente mediante configuración.
  2. Congelar cambios mayores en legado: Durante la refactorización, no agregar nuevas funcionalidades al código legacy. Todo nuevo desarrollo debe hacerse en v2.
  3. Testing primero: No comenzar la refactorización de un módulo sin antes tener tests de caracterización del módulo legacy.
  4. CI/CD con validación automática: El pipeline debe ejecutar tests de caracterización + equivalencia antes de cada deploy.
  5. Pair programming en módulos críticos: M07 (Facturación/ECF) y M08 (Contabilidad) deben desarrollarse en pair programming por su complejidad y riesgo.
  6. Documentación viva: Mantener ARCHITECTURE.md actualizado con cada módulo refactorizado.
  7. Sprint reviews semanales: Demostrar avances cada viernes para mantener la visibilidad del progreso.
  8. Métrica de éxito: Cada módulo v2 debe pasar el 100% de los tests de equivalencia antes de considerar "completado".
