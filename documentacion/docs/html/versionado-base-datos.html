Versionado de la Base de Datos

Cómo pasamos de una base tocada a mano —sin control de nada— a un sistema con migraciones y datos de fábrica, que se replica solo a cada cliente, sin tocar el código viejo. Paso a paso, y qué gana el sistema en cada uno.

El problema de fondo: como cada cambio se hace a mano y en cada base por separado, hoy nadie puede garantizar que la base de un cliente sea igual a la de otro. Pueden haber divergido sin que nadie lo sepa, hasta que algo rompe en un solo cliente.
La idea en una frase

Qué significa "versionar" la base

Es ponerle a la base de datos el mismo control de versiones que ya usás para el código (git). Cada cambio de estructura queda escrito, numerado y guardado. La base deja de cambiarse a mano: cambia solo aplicando esos scripts, en orden, y siempre sabés en qué versión está cada cliente.

📜 Migración

Un cambio de estructura: una tabla nueva, una columna, un índice. Es "un commit" de la base.

🌱 Seeder

Los datos de fábrica: monedas, países, catálogos base que toda base necesita para arrancar.

El camino, paso a paso

Cómo llegamos ahí

Cinco pasos, en orden. Cada uno se apoya en el anterior. Debajo de cada paso: en qué ayuda de verdad.

0

Hoy — V000, sin versionar

La base funciona, pero nadie controla su estructura. Cada cambio es manual y no queda registro.

Por qué hay que salir de acá: un cambio mal aplicado en un cliente no se detecta, y no hay forma de saber qué versión tiene cada base.
▼
1

Baseline — la foto de partida V001

Se toma una "foto" del schema actual (las 92 tablas, los 42 SPs) y se guarda como el primer script versionado. Es el punto cero oficial.

En qué ayuda: a partir de acá, la estructura actual queda escrita y guardada en git. Es la referencia contra la cual se compara todo. Sin esto no se puede empezar.
▼
2

Migraciones incrementales V002, V003…

De ahí en más, cada cambio de estructura se escribe como un script nuevo numerado. Nunca más se toca la base a mano.

En qué ayuda: cada cambio queda auditado (quién, cuándo, qué) y se puede aplicar a todos los clientes con un comando. Se acabó el "lo cambié en producción y no me acuerdo qué toqué".
▼
3

Seeders — los datos de fábrica

Los datos base que toda instalación necesita (monedas, catálogos, países) se escriben como scripts que se pueden correr sin duplicar nada.

En qué ayuda: una base nueva no nace vacía ni hay que cargar datos a mano. Los datos de referencia llegan solos y son iguales para todos los clientes.
▼
4

Base nueva desde cero — cliente nuevo al día

Con el baseline + las migraciones + los seeders, crear la base de un cliente nuevo es correr todo en orden, automático.

En qué ayuda: un cliente nuevo nace con la estructura y los datos correctos y actualizados, sin copiar bases a mano ni riesgo de olvidarse algo. Hoy eso se hace copiando una plantilla manualmente.

Detalle

Seeders: qué son y en qué ayudan

Un seeder carga datos, no estructura. Hay dos tipos y no se mezclan.

🌱 Datos de referencia

Monedas, países, catálogos base. Van versionados y son idempotentes (si ya existen, no los duplica). Toda base los recibe.

Ayuda: un cliente nuevo arranca con los datos base correctos, sin carga manual.

🧪 Datos de prueba

El usuario y la empresa de test. Viven aparte, solo para el entorno de tests. Ya existe uno en el proyecto.

Ayuda: los tests corren siempre contra los mismos datos conocidos, sin tocar producción.
El corazón multi-cliente

Cómo un cambio llega a todos los clientes

Cada cliente tiene su propia base. La clave: se escribe el cambio UNA vez, y el ejecutor lo lleva a cada base aplicando solo lo que le falta.

La regla de oro

Todo esto sin tocar el código viejo

El versionado de la base es un frente separado del código. Vive en scripts SQL, no en el C# de siempre. Por eso avanza sin riesgo para lo que hoy está en producción.

✓ No toca nada

Escribir scripts, versionar, sembrar datos, consultar versiones. Son archivos nuevos y lecturas. El código viejo ni se entera.

⚠ El único matiz (opcional)

Si se quiere que la app aplique las migraciones sola al arrancar → 1 línea al arranque. Recomendado: que el ejecutor corra aparte → cero toque.

Dónde se cruzan los dos frentes: solo cuando un módulo nuevo necesita un cambio de estructura, ese cambio entra como una migración versionada. El frente de código "pide", el de base "provee" — cada uno en su carril, y el viejo sigue intacto.
