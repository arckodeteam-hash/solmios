1

Crear las BDs _test en el server online

VERIFICAR AL FINAL

El script setup-test-db.sh ya tiene modo remoto (variable KAPTAS_SQL_HOST). Esto crea kaptaswebdev_test y kw21_test en el server online, como copia de las dev, vía BACKUP/RESTORE.

Comando
# Apunta al server online + su password
KAPTAS_SQL_HOST=173.249.31.75 \
KAPTAS_SA_PASSWORD='Motoya2026!' \
bash Kaptas.Tests/scripts/setup-test-db.sh
Qué hace (automático)
→Verifica que el server online responde.
→BACKUP de kaptaswebdev + RESTORE como kaptaswebdev_test.
→Lo mismo con kw21 → kw21_test.
→Aplica el seed (usuario proquia@gmail.com + permisos).
→Crea el snapshot limpio (*_clean.bak) para resets rápidos.
⚠️ Importante: esto crea BDs nuevas (_test) en el server online. No toca las BDs existentes (kaptaswebdev, kw21, tenants). Es seguro.
Cómo verificar que funcionó
# Debe listar kaptaswebdev_test y kw21_test
docker exec kaptas-sql /opt/mssql-tools18/bin/sqlcmd \
  -S 173.249.31.75 -U SA -P 'Motoya2026!' -C -h-1 -W \
  -Q "SELECT name FROM sys.databases WHERE name LIKE '%_test';"

Resultado esperado: 2 filas (kaptaswebdev_test, kw21_test).

2

Hacer que los tests apunten al server online

VERIFICAR AL FINAL

Los tests ya leen los connection strings de variables de entorno (no hay que tocar código). Solo seteás las vars antes de correr.

Variables (para correr contra el server online)
# Apuntan las BDs _test del server online
export TEST_DB_WEB_TEST="Server=173.249.31.75,1433;Initial Catalog=kaptaswebdev_test;User ID=SA;Password=Motoya2026!;TrustServerCertificate=True;"
export TEST_DB_TENANT_TEST="Server=173.249.31.75,1433;Initial Catalog=kw21_test;User ID=SA;Password=Motoya2026!;TrustServerCertificate=True;"

dotnet test Kaptas.Tests/Kaptas.Tests.csproj
Mi recomendación: guardá esas variables en un archivo .env.tests (ignorado por git) y lo cargás con set -a; source .env.tests; set +a. Así no las tipeás cada vez y nunca quedan en el repo.
Cómo verificar

Corré dotnet test --filter "FullyQualifiedName~LoginTests". Si pasa, los tests están leyendo del server online. Si tira error de conexión, revisá las variables.

⚠️ Seguridad: la password nunca va en el repo ni commiteada. Solo en variables de entorno o en GitLab CI/CD Variables (masked).
3

Crear el reset automático para CI (.gitlab-ci.yml)

POR CREAR

En CI, antes de correr los tests hay que resetear las BDs _test del server online. Esto va en el pipeline.

.gitlab-ci.yml (archivo nuevo en la raíz del repo)
test:
  image: mcr.microsoft.com/dotnet/sdk:7.0
  variables:
    # Credenciales desde CI/CD Variables (secret, masked)
    KAPTAS_SQL_HOST: "173.249.31.75"
    KAPTAS_SA_PASSWORD: $KAPTAS_SA_PASSWORD   # ← definir en GitLab Settings → CI/CD → Variables
    TEST_DB_WEB_TEST: $TEST_DB_WEB_TEST
    TEST_DB_TENANT_TEST: $TEST_DB_TENANT_TEST
  script:
    - dotnet restore
    - dotnet build
    - bash Kaptas.Tests/scripts/setup-test-db.sh --reset-only   # resetea _test en el remoto
    - dotnet test Kaptas.Tests/Kaptas.Tests.csproj
En GitLab: definir estas variables (Settings → CI/CD → Variables, marcadas como Masked)
•KAPTAS_SA_PASSWORD = la password del server online
•TEST_DB_WEB_TEST = string de conexión a kaptaswebdev_test
•TEST_DB_TENANT_TEST = string de conexión a kw21_test
⚠️ Detalle del runner: el script usa docker exec (necesita el contenedor kaptas-sql como cliente sqlcmd). En CI hay 2 opciones: (a) un runner con Docker que tenga el contenedor, o (b) instalar mssql-tools18 en la imagen del job. Recomendado: (b) — cambiar el script para usar sqlcmd directo cuando no hay Docker.
Cómo verificar

Hacé un push y mirá el pipeline en GitLab. El job test debe terminar verde con "239 passed".

4

(Opcional) Mantener el server actualizado ← prod

DBA

Para que el server de prueba no se quede "lejos de lo actual", un job nocturno (cron / SQL Agent) que restaura las BDs base desde prod.

Flujo del job nocturno (lo arma el DBA)
→BACKUP DATABASE kaptaswebdev (en prod) → copia el .bak al server de prueba.
→RESTORE en el server de prueba (sobrescribe kaptaswebdev, kw21).
→Correr de nuevo la Fase 1 para regenerar las _test + snapshot limpio.
⚠️ Datos sensibles: al sincronizar con prod, el server de prueba tendrá datos reales. Asegurate de que el acceso esté restringido. Si hay datos sensibles (pagos, RNCs), evaluá desidentificarlos.
Mi recomendación: sync semanal o antes de cada release. No hace falta diario si el schema cambia poco.
