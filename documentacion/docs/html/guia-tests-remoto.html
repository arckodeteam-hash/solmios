Tests de Kaptas — sin Docker, contra el server online

Cómo funciona el sistema de tests aislados y cómo lo reproduce cualquiera · verificado 2026-07-01

1️⃣ El problema que esto resuelve

Kaptas no puede testear como Laravel o Rails. En esos frameworks la BD se crea desde código (migraciones): cada test run arma la BD limpia. En Kaptas eso es imposible:

📦 Sin migraciones

El schema (tablas, columnas) lo crea el DBA a mano en la BD física. No hay EF migrations.

⚙️ SPs en SQL Server

La lógica de negocio (usp_generar_menu, P_Operacion_...) vive dentro de SQL Server, no en código.

🧪 Tests los necesitan

Los tests de integración requieren ese schema + SPs + datos para correr.

🔑 Conclusión: sin migraciones, la única fuente de verdad del schema es una BD física que ya existe. No se puede "crear desde cero" — hay que partir de una BD real.

2️⃣ La idea central: AISLAR COPIANDO

Como no podés crear la BD desde scripts, la copiás. Tomás una BD buena (la dev) y la duplicás en una copia descartable (la _test). Los tests pegan contra la copia. La original nunca se toca.

4️⃣ Flujo de SETUP (1 vez, o cuando cambia el schema)

Cuando ejecutás bash setup-test-db.sh:

  1. ensure_sqlcmd() — verifica que sqlcmd esté en el PATH y que el destino ($SQL_HOST) responda.
  2. resolve_backup_dir() — ¿/var/opt/mssql/backup existe en el destino? SÍ → lo usa. NO → cae a /var/opt/mssql/data (fallback automático).
  3. Validar proquia — aborta si el usuario de prueba no existe en la dev.
  4. create_test_db() ×2 — BACKUP dev → RESTORE _test (copia schema+SPs+datos).
  5. apply_seed() — sobre kaptaswebdev_test: asegura rol 300 con todos los permisos, password de proquia, tenant correcto.
  6. make_clean_snapshot() — BACKUP de cada _test (post-seed) → *_clean.bak. Este es el "punto de guardado" limpio.

5️⃣ Flujo de RESET (antes de cada dotnet test)

El reset no recrea desde la dev (lento). Restaura desde el snapshot limpio guardado en el setup:

  1. snapshot_exists()? — confirma que *_clean.bak existe (sino aborta).
  2. SET SINGLE_USER — mata conexiones abiertas a la _test.
  3. RESTORE ... WITH REPLACE — pisa la _test con el snapshot limpio (~0.6s de SQL).
  4. SET MULTI_USER — vuelve a permitir conexiones.
⏱️ El reset es barato (~9s con latencia de red; el SQL puro son ~0.6s a ~900 MB/s). Por eso corre automáticamente antes de cada test run (un target de MSBuild lo dispara). Garantiza estado reproducible: si un test muta datos, el siguiente run los "olvida".

7️⃣ Los 3 trucos que lo hacen robusto

🔀 Fallback de BACKUP_DIR

Problema: el server online no tiene /var/opt/mssql/backup.

Solución: resolve_backup_dir() usa xp_fileexist; si no existe, cae a /var/opt/mssql/data. Automático, sin SSH ni xp_cmdshell.

🧬 Seed tolerante a IDENTITY

Problema: en el remoto las tablas son IDENTITY, en el local no (drift de schema).

Solución: antes de cada INSERT, el seed chequea sys.columns.is_identity y hace SET IDENTITY_INSERT ON solo si corresponde. Funciona en ambos.

🔎 Reset vía SQL

Problema: el .bak vive en el server, no en tu máquina.

Solución: snapshot_exists usa RESTORE HEADERONLY (consulta SQL) en vez de test -f del filesystem.

🐛 Bug histórico que se arregló: el reset pasaba un path de tu máquina a sqlcmd que corría en otro contexto → fallaba silenciosamente y un || true ocultaba el error. El reset "funcionaba" sin resetear nada. Ahora captura el código de salida y die si falla.

8️⃣ Cómo lo reproduce cualquiera

Paso 1 — Instalar sqlcmd (1 vez, sin Docker ni sudo)

# go-sqlcmd (standalone, driver embebido, ~22 MB)
curl -L https://github.com/microsoft/go-sqlcmd/releases/latest/download/sqlcmd-linux-amd64.tar.bz2 \
  | tar xj -C ~/.local/bin sqlcmd && chmod +x ~/.local/bin/sqlcmd
sqlcmd --version   # verificar

Windows/Mac: usá sqlcmd-windows-amd64.zip / sqlcmd-darwin-* del mismo release.

Paso 2 — Setup + reset contra el server online

# Credenciales por ENV (una vez por sesión — NUNCA en git)
export KAPTAS_SQL_HOST="173.249.31.75,1433"
export KAPTAS_SA_PASSWORD="<pedila al equipo>"

bash Kaptas.Tests/scripts/setup-test-db.sh              # setup 1 vez (~20 s)
bash Kaptas.Tests/scripts/setup-test-db.sh --reset-only # reset cuando quieras (~9 s)
dotnet test Kaptas.Tests/Kaptas.Tests.csproj            # correr los tests

9️⃣ Advertencias

🔐 Credenciales NUNCA en el repo

La password del server online no se commitea. Se pasa por export temporal. En el repo no hay ninguna credencial del remoto.

🔀 Drift de schema

El remoto puede tener un schema más nuevo que el local (más SPs, columnas IDENTITY). El setup+reset funcionan igual (copian lo que haya), pero tests escritos para el schema local pueden comportarse distinto. Se ajusta por separado.

🎬 Resumen en 3 frases

1. Como no hay migraciones, copiamos una BD buena (dev) a una descartable (_test) con BACKUP/RESTORE — schema, SPs y datos viajan juntos.
2. Guardamos un snapshot limpio tras el seed, y cada test run lo restaura → estado reproducible, sin contaminación.
3. El destino se elige con una variable de entorno, con sqlcmd nativo — sin Docker, mismo script, cero credenciales en el repo.
