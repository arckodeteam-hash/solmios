🧠 Flujo de Trabajo Kaptas ERP — Explicado

Cómo trabajar sin pisarse, sin heredar bugs ajenos y entendiendo cuándo usar release

🔍 Las 3 Etapas de Prueba (y quién revisa qué)
🧪 Etapa 1 — En tu rama (TÚ)

Codeas y pruebas tu feature en tu propia rama.
Si encuentras bug, lo corriges ahí mismo.
➜ Verificas que TU código funciona SOLO.

🔬 Etapa 2 — QA-DEV (Joel/José)

Revisan que tu código esté bien escrito: seguridad, arquitectura, buenas prácticas.
➜ NO prueban funcionalidad. Revisan el código.

🧪 Etapa 3 — QA-UI (Equipo Kaptas)

Prueban todo junto en pre-produccion: tu feature + las de otros.
Aquí aparecen los bugs de integración: "el botón de A se rompe cuando B está activo".
➜ Prueban funcionalidad, UI/UX, frontend + backend juntos.

❓ ¿Por Qué Necesitamos release/vX.X.X?
😱 Escenario sin release

DEV 01 termina Feature A → QA-DEV aprueba ✅
DEV 02 termina Feature B → QA-DEV aprueba ✅

QA-UI prueba ambas juntas en pre-produccion:
"Feature A rompe el frontend cuando Feature B está activa" ❌

¿Desde dónde creo el fix?
❌ main → El bug NO existe, A y B no están en main
❌ pre-produccion → Tiene WIP de otros, me llevo basura
✅ release/vX.X.X → Tiene EXACTAMENTE A + B. El bug está aquí.

✅ Solución: release branch

release/vX.X.X se crea desde main y solo contiene features aprobadas por QA-DEV.

No es lo mismo que pre-produccion:
• pre-produccion = WIP de todos, código inestable
• release = solo features listas para producción

El fix se crea desde release, se mergea a release,
y release va a main cuando QA-UI aprueba.

📋 Tabla Decisoria: ¿Desde Dónde Creo Mi Rama?
Situación Crear desde Explicación
✨ Feature nueva main Arrancas limpio, sin código de nadie
♻️ Refactor main Mejoras código que ya está en producción
🔧 Bug en desarrollo (tu PC) Tu misma rama Corriges y push, sin crear rama nueva
🔧 Bug en QA-DEV (PR) Tu misma rama Corriges, push, el PR se actualiza solo
🔧 Bug en QA-UI (pruebas) release/vX.X.X El bug está en la release. Desde main no existe. Desde release sí puedes reproducirlo.
🚨 Hotfix (producción) main Urgente, el bug está en vivo
🧠 Resumen fácil de recordar

¿Es trabajo nuevo? → main
¿Es un bug en algo que ya está en pruebas? → release/vX.X.X
¿Es un bug en tu propia rama? → Ahí mismo, sin crear rama nueva
¿Es un bug en producción? → main (hotfix)

🛡️ Reglas para No Heredar Errores de Otros
✅ SÍ

✓ Crear ramas desde main
✓ Probar en tu propia rama antes del PR
✓ PRs pequeños (menos de 400 líneas)
✓ Hacer git rebase main antes del PR
✓ Que otro revise tu código (nadie se auto-aprueba)
✓ Bugs en QA-UI → fix desde release/vX.X.X

❌ NO

✗ Crear ramas desde pre-produccion
✗ Crear ramas desde ramas de otros
✗ Mergear tu propio PR
✗ Crear fix de bug en pruebas desde main
✗ Resolver conflictos por la web de GitHub
✗ Codear sin hacer git pull primero

⚠️ ¿Conflicto en el PR? Hacemos así

1. git checkout main && git pull
2. git checkout feature/mia
3. git rebase main
4. Resuelves conflictos UNO POR UNO
5. git push --force-with-lease

¿Muchos conflictos (10+ archivos)?
Mejor crea nueva rama desde main y re-aplica tus cambios manualmente.

🤔 Preguntas Frecuentes
"Pero si release va a main igual, da lo mismo crear desde main"

No. main hoy NO tiene la feature bug-eada (no ha llegado a producción). Si creas desde main, codeas sobre código que no se parece al entorno de pruebas. El fix no funciona porque los archivos que necesitas tocar no existen en tu base.
Desde release sí existen. Por eso se usa release.

"Si pruebo todo en mi rama, ¿para qué necesito pre-produccion?"

En tu rama pruebas tu código solo. Pero tu feature puede romper el frontend cuando se encuentra con la feature de otro. Eso solo se descubre cuando todo está junto en pre-produccion.

"¿Por qué no creo el fix desde pre-produccion si ahí está el bug?"

Porque pre-produccion tiene WIP de todos los DEV: features a medio hacer, bugs sin corregir, experimentos. Si creas tu rama desde ahí, te llevas todo eso sin saberlo y tu PR tendrá errores que no son tuyos.
Desde release solo tienes features aprobadas.
