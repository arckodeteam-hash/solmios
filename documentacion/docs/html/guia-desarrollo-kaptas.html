Guía de Desarrollo — Kaptas Web API

Documento canónico para todo el equipo. Explica los 3 ciclos de trabajo (feature nueva, refactor, bug fix), las reglas obligatorias, la estructura de módulos y cómo escribir tests. Si algo no está acá, no se hace.

🔒 Reglas de Oro — aplican a los 3 ciclos

Estas reglas no son negociables. Si las rompés, el código no pasa revisión. Están pensadas para que el sistema crezca sin romperse.

🛡️ Lo que SIEMPRE se hace

  • Tests ANTES de tocar código. Si no hay test que capture el comportamiento actual, no se modifica nada. Sin excepción.
  • Endpoints NO cambian. La URL, el método HTTP, el request y el response se mantienen idénticos. El frontend no debe enterarse de que el backend cambió.
  • Controller flaco (~30 líneas). Solo recibe HTTP, llama al service, retorna HTTP. Cero lógica de negocio en el controller.
  • IdCompany en TODA query. Cada consulta a la BD filtra por la empresa del usuario. Es lo que evita que un cliente vea datos de otro.
  • AsNoTracking() en toda lectura. Si no vas a modificar la entidad, no la trackees.
  • DateTime.UtcNow, nunca DateTime.Now. La zona horaria la maneja el frontend.

☠️ Lo que NUNCA se hace

  • NO se toca BaseService. Nunca. Ni para arreglar algo "de paso". Esa clase se eliminará cuando todos los módulos migren, no antes.
  • NO se importa Kaptas.Services desde un módulo nuevo de Features/. Lo nuevo no depende de lo viejo.
  • NO se hereda de BaseService en ningún módulo nuevo. Se usa ICurrentUserProvider.
  • NO se borra un test "para que compile". Si un test falla, se investiga por qué. Borrarlo es esconder el problema.
  • NO se arregla un bug sin poder reproducirlo primero. Sin reproducción no hay certeza de que se arregló.
  • NO se modifican las BDs dev (kaptaswebdev / kw21) desde tests. Los tests usan BDs _test aisladas.

🗺️ Las 3 zonas del código

Todo el código de Kaptas está en una de estas 3 zonas. El trabajo de cada ciclo es mover módulos hacia la derecha.

💀

LEGADO

Kaptas.Services/
Sin tests, depende de BaseService

🔗

PUENTE

Features/ + viejo vivo
Ambos conviven, feature flag activa

✅

LIMPIO

Features/ únicamente
Viejo eliminado, con tests

¿Cómo se mueve un módulo de LEGADO → LIMPIO?

Cada vez que hacés un CICLO RECICLADO a un módulo, lo movés una casilla a la derecha. Primero queda en PUENTE (conviven viejo y nuevo). Cuando confirmás que el nuevo funciona, eliminás el viejo y el módulo queda LIMPIO. Nunca se salta la zona PUENTE.

✨ Ciclo 1 — VERDE (Feature nueva)

Cuando llega un pedido de algo que no existe hoy. Se crea desde cero, bien hecho, en Features/.

✨

VERDE — Módulo nuevo desde cero

¿Cuándo? → Feature nueva que no existe en el sistema
📦 Ejemplo real: un cliente pide gestionar inventario (stock de productos). Eso no existe hoy. Se crea desde cero en Features/Inventario/.
FASE A — Análisis (sin código)
  1. Definí qué tablas ESCRIBE el módulo

    Tablas donde hace INSERT / UPDATE / DELETE. Son las tablas "propias" del módulo.

    Por qué: define el alcance de escritura. Nadie más debería escribir esas tablas directamente.
  2. Definí qué tablas SOLO LEE

    Catálogos, referencias, datos de otros módulos que consulta pero nunca modifica.

    Por qué: identifica dependencias de lectura sin acoplamiento de escritura.
  3. Identificá módulos DEPENDIENTES

    ¿Qué otros módulos van a leer de tus tablas? (ej: Ventas lee Contactos para mostrar el nombre del cliente).

    Por qué: saber el impacto. Si tu módulo es central, 10+ módulos pueden leer de él.
  4. Listá los permisos necesarios

    Claims JWT que controlan el acceso (ej: INVENTARIO, VERPRECIOS).

    Por qué: cada endpoint debe tener su [Authorize(Roles="...")].
  5. Definí los endpoints HTTP

    Método + ruta + qué recibe + qué devuelve. Documentalos antes de programar.

    Por qué: la API se define primero. Es el contrato con el frontend.
FASE B — Estructura
  1. Creá la carpeta Features/[Modulo]/

    Con subcarpetas: DTOs/. Todo lo del módulo vive junto.

    Por qué: cada módulo es autocontenido. No se desparrama en 4 proyectos.
  2. Creá los DTOs primero

    [X]DetailDto, [X]ListDto, [X]CreateRequest, [X]UpdateRequest, [X]ListRequest.

    Por qué: los DTOs definen la forma de los datos. El resto del módulo se construye alrededor de ellos.
  3. Creá la interfaz I[X]Service.cs

    El contrato: qué métodos expone el módulo. Solo firmas, sin implementación.

    Por qué: definir la API del módulo antes de implementarla obliga a pensar el diseño.
FASE C — Implementación (de adentro hacia afuera)
  1. Implementá [X]Service.cs

    La lógica de negocio. Validaciones, reglas, acceso a BD. Usa ICurrentUserProvider (no BaseService).

    Por qué: el service es el corazón. Todo lo demás es piel.
  2. Implementá [X]Controller.cs (~30 líneas)

    Solo recibe HTTP, llama al service, retorna HTTP. Nada de lógica.

    Por qué: controller flaco = fácil de testear y mantener.
FASE D — Tests y cierre
  1. Escribí los tests

    Mínimo: crear válido, crear inválido, listar paginado, detalle existente, detalle inexistente, eliminar, aislamiento tenant.

    Por qué: sin tests, cualquier cambio futuro puede romper el módulo sin aviso.
  2. Build + tests verdes + commit

    dotnet build sin errores, dotnet test todo verde, commit con prefijo feat:.

    Por qué: es el checkpoint de calidad. Si algo falla, no se mergea.

♻️ Ciclo 2 — RECICLADO (Refactorizar módulo existente)

Cuando un módulo ya existe en Kaptas.Services pero está hecho un lío (depende de BaseService, sin tests, 700+ líneas en un archivo).

♻️

RECICLADO — Migrar de Services → Features

¿Cuándo? → Módulo viejo que necesita orden, o acumuló 3+ bugs
📦 Ejemplo real: ContactService (735 líneas, 8 dependencias inyectadas, 0 tests). Se migra a Features/Contactos/ sin cambiar ningún endpoint.
  1. Escribí tests de caracterización

    Tests que capturen lo que el módulo HACE hoy, no lo que debería hacer. Si hoy devuelve 5 contactos, el test verifica que devuelve 5. No importa si está bien o mal — solo documentar el comportamiento real.

    OBLIGATORIO Sin esto, cualquier cambio es a ciegas. Si no sabés qué hace hoy, no podés saber si lo rompiste. Este paso no se salta nunca.
  2. Creá el módulo nuevo en Features/[Modulo]/

    Con su propio Controller + Service + DTOs. Mismos endpoints, misma lógica, pero sin BaseService. El viejo sigue vivo — no se borra nada todavía.

    Por qué: el módulo entra en zona PUENTE. Viejo y nuevo conviven.
  3. Activá el nuevo para UN solo cliente con feature flag

    Un interruptor que manda a 1 cliente al nuevo; los demás siguen en el viejo. Si algo falla, solo falla para ese cliente y se puede revertir en segundos.

    Por qué: migrar todo de golpe = riesgo de romperle el sistema a todos los clientes a la vez.
  4. Migrá al resto de clientes de a uno

    Cliente por cliente, verificando que todo funcione. Sin apuro.

    Por qué: lento pero seguro. Cada cliente migrado es un cliente verificado.
  5. Eliminá el viejo

    Cuando nadie usa el módulo viejo: lo marcás [Obsolete] por una iteración, y después lo borrás. El módulo queda LIMPIO.

    Por qué: solo se borra cuando hay certeza absoluta de que el nuevo funciona para todos.

⚠️ Crítico: endpoints idénticos

  • Misma URL, mismo método HTTP, mismos parámetros.
  • Mismo formato de response. Mismos códigos de error.
  • El frontend no debe notar la diferencia. Si el frontend necesita cambios, algo se hizo mal.
  • Cada endpoint del viejo debe tener su equivalente exacto en el nuevo.

🐛 Ciclo 3 — PARCHE (Arreglar bug)

Cuando alguien reporta que algo no funciona. Puede estar en código viejo (Services) o nuevo (Features). El procedimiento cambia según dónde esté.

🐛

PARCHE — Reparar algo que no funciona

¿Cuándo? → Bug reportado por cliente, error 500 en logs, o comportamiento incorrecto
📦 Ejemplo real: un cliente reporta que ve facturas de otra empresa. Es un problema de tenant (falta el filtro IdCompany en una consulta). Hay que arreglarlo YA.
  1. Detectá el origen del aviso

    Del log (dbo.Log en la BD), del reporte del cliente, de un error 500, o del dashboard de Hangfire. Necesitás datos concretos: ¿qué usuario? ¿qué endpoint? ¿qué datos devolvió? ¿qué debería haber devuelto?

    Sin datos del problema, estás adivinando.
  2. ESCRIBÍ EL TEST QUE REPRODUCE EL BUG OBLIGATORIO

    Antes de arreglar nada, creá un test que falle con el bug. Ejecutalo y confirmá que está ROJO. Este test es tu prueba de que el bug existe y tu garantía de que no vuelve.

    OBLIGATORIO Si no podés reproducirlo en un test, no sabés si lo arreglaste. No se arregla a ciegas.
  3. Ubicá dónde está el código

    ¿Está en Kaptas.Services/ (viejo) o en Features/ (nuevo)? Esto determina cómo se arregla.

    No es lo mismo operar en código sin tests que en código con tests.
  4. Buscá la causa raíz, no el síntoma

    "¿Por qué ve facturas ajenas?" → falta el filtro IdCompany en esa consulta. "¿Por qué el login falla con mayúsculas?" → comparación case-sensitive sin ToUpper(). No parches el síntoma — arreglá la causa.

    Parchear el síntoma hace que el bug vuelva por otro camino. Hay que ir a la raíz.
  5. Arreglá según dónde esté

    Si está en lo VIEJO (Services): hacé el parche mínimo para resolver el bug. No refactorices todo el módulo "de paso". Anotá el módulo para entrar al CICLO RECICLADO.

    Si está en lo NUEVO (Features): arreglalo y además escribí/mejorá los tests del módulo para cubrir ese caso.

    Arreglar a fondo el viejo sin tests = alto riesgo de romper otra cosa. Mejor anotarlo y reciclarlo con calma.
  6. El test del bug queda para siempre

    El test que escribiste en el paso 2 ahora pasa a VERDE. Ese test nunca se borra. Es tu red de seguridad: si alguien reintroduce el bug, el test lo detecta.

    Un bug que ya pasó una vez no debería volver a pasar nunca más.
🔗 Regla de conexión entre ciclos: si un módulo viejo acumula 3+ bugs, ese módulo sube al tope de la lista para entrar al CICLO RECICLADO. El bug de hoy es la señal de qué hay que limpiar mañana.

📂 Estructura de un módulo en Features/

Todo módulo nuevo o migrado vive acá. La estructura es fija y todos los módulos la siguen.

Features/[Modulo]/
│
├── DTOs/                        ← QUÉ datos entran y salen
│   ├── [X]DetailDto.cs         ← Response: detalle completo
│   ├── [X]ListDto.cs           ← Response: item en listado
│   ├── [X]CreateRequest.cs     ← Request: datos para crear
│   ├── [X]UpdateRequest.cs     ← Request: datos para actualizar
│   └── [X]ListRequest.cs       ← Request: filtros de búsqueda
│
├── I[X]Service.cs          ← CONTRATO: qué puede hacer el módulo
├── [X]Service.cs           ← IMPLEMENTACIÓN: lógica de negocio
│
├── [X]Controller.cs        ← ENDPOINTS HTTP (~30 líneas máximo)
└── README.md                    ← Documentación del módulo

Qué va en CADA archivo

ArchivoContenidoEjemplo
DTOs/ Clases que definen la forma de los datos ContactoDetailDto tiene Nombre, Apellido, Documento
I[X]Service.cs Interface con métodos: Crear, Listar, Obtener, Actualizar, Eliminar Task<int> CrearAsync(ContactoCreateRequest req)
[X]Service.cs Implementación — toda la lógica de negocio, validaciones, acceso a BD Validar que el nombre no esté vacío, filtrar por IdCompany, guardar en BD
[X]Controller.cs Endpoints HTTP — ~30 líneas máximo Recibe POST → llama a _service.CrearAsync(req) → retorna 201
💡
¿Y si el módulo necesita queries complejas (Dapper / Stored Procedures)?
Se agrega un I[X]Repository.cs + [X]Repository.cs en la misma carpeta. El service lo inyecta. Pero no es obligatorio — solo si EF Core no alcanza.

Dependencias permitidas y prohibidas

✅ PERMITIDO❌ PROHIBIDO
ICurrentUserProvider (desde Features/_Shared/) IBaseService / BaseService
KaptasCoreContext / KaptaswebContext Kaptas.Services (cualquier namespace)
Kaptas.DTO (para DTOs compartidos) ISpExecute / IDbService
Kaptas.Helpers (crypto, settings) Heredar de cualquier clase de Services/

🧪 Tests — cómo y cuándo escribirlos

Los tests son obligatorios en los 3 ciclos. Sin tests no hay merge. El proyecto Kaptas.Tests tiene 2 tipos de tests.

Los 2 tipos de test (y para qué sirve cada uno)

TipoCarpetaDónde correTiempoCuándo se usa
Unitarios Features/ Sin BD (mocks) ~1 segundo Lógica pura: validaciones, crypto, cálculos, reglas de negocio
Integración Legacy/ Contra BD _test aislada ~45 segundos Queries reales, SPs, flujos completos, caracterización de módulos viejos

Matriz: qué tests escribir según el ciclo

CicloTipo de testQué probarCuándo se escribe
✨ VERDE Unitarios + Integración Crear válido/inválido, listar, detalle, eliminar, aislamiento tenant Después del service, antes del controller
♻️ RECICLADO Caracterización (Integración) Lo que HOY hace el módulo viejo (sin juzgar si está bien o mal) ANTES de tocar una línea de código
🐛 PARCHE Regresión (Unitario o Integración) El caso exacto que reproduce el bug ANTES de arreglar el bug (debe fallar en rojo)

Cómo correr los tests

# Setup inicial (solo la primera vez)
bash Kaptas.Tests/scripts/setup-test-db.sh

# Todos los tests
dotnet test

# Solo unitarios (sin BD, ~1s)
dotnet test --filter "Category=Unit"

# Solo integration (contra BD _test)
dotnet test --filter "Category=Integration"

# Un test específico
dotnet test --filter "FullyQualifiedName~LoginTests"

# Saltar reset de BD (para CI o corridas repetidas)
dotnet test /p:SkipDbReset=true

⚠️ Las BDs aisladas

  • Los tests nunca tocan kaptaswebdev ni kw21.
  • Trabajan sobre copias kaptaswebdev_test / kw21_test.
  • Antes de cada dotnet test, el sistema restaura las _test desde un snapshot limpio.
  • Si las _test no existen, corré bash Kaptas.Tests/scripts/setup-test-db.sh una vez.

✅ Checklist universal de cierre

Antes de decir "listo", recorré esta lista. Aplica a los 3 ciclos por igual.

Build y tests

dotnet build = 0 errores, 0 warnings nuevos
dotnet test = todos verdes (unitarios + integración)

Calidad del código nuevo

Controller tiene ~30 líneas (no más de 50)
No importa Kaptas.Services
No hereda de BaseService ni usa IBaseService
Toda query filtra por IdCompany
Toda lectura usa AsNoTracking()
Usa DateTime.UtcNow (no DateTime.Now)
Todos los [Authorize] están activos (no comentados)

Endpoints (para RECICLADO)

Misma URL, mismo método HTTP que el viejo
Mismo request body y response shape
Mismos códigos de respuesta (200, 201, 400, 404, 500)
El frontend no necesita ningún cambio

Documentación y repo

README.md en la carpeta del módulo (opcional pero recomendado)
Commit con prefijo: feat: / refactor: / fix:

☠️ Si algo de esto no se cumple, el código NO se mergea

  • Build rojo o tests rojos → no merge
  • Controller de 200 líneas con lógica adentro → no merge
  • Importa Kaptas.Services desde Features/ → no merge
  • Consulta sin filtro IdCompany → no merge
  • Bug arreglado sin test de regresión → no merge
  • Módulo reciclado sin tests de caracterización → no merge
