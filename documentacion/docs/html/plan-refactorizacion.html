◍ Lo que hay

  • Lógica repartida en 90 services que heredan de un BaseService monolítico.
  • 21 procedimientos almacenados (SPs) con lógica de negocio fuera del ORM.
  • Schema de base de datos tocado a mano, sin control de versión.
  • Sin tests que atajen un bug antes de producción.
  • No hay forma de saber qué módulo ya se limpió y cuál no.

◉ A dónde vamos

  • Módulos limpios y aislados en Features/, uno por uno, sin apagar el sistema.
  • Cada módulo con sus tests que congelan el comportamiento correcto.
  • Base de datos versionada: cada cambio auditado y aplicado a todos los clientes.
  • Un tablero (REGISTRO-MODULOS.md) que dice el estado real de cada módulo.
  • Acceso a datos consolidado en el ORM, con lo pesado optimizado.
Medido en el código

El inventario: 90 módulos en 3 grupos de dificultad

Por cada service medimos 4 cosas — cuántas dependencias tiene, si usa el BaseService, si llama SPs, y si depende del contexto HTTP. Eso determina cuánto cuesta testearlo y define el orden: se empieza por lo más simple.

TIER 1 · empezamos acá

Se prueban solos: new Service(contexto). Sin trucos. Ejemplos: ContactAddresses, Zonas, Paradas, Choferes, módulos contables.

TIER 2 · el grueso

Necesitan base de datos real para probarse. Aquí vive la mayoría del negocio: Ventas, Compras, Facturación, Inventario.

TIER 3 · al final

Piden levantar la API entera para testear. Son 5: Auth, KProducts, Payroll, Notifications, Language. Los más caros y riesgosos.

Por eso Auth NO es el primero. Es el módulo más atado del sistema (16 dependencias, 1.680 líneas). Empezar por él sería empezar por el escalón más alto. Va al final, cuando ya tengamos módulos limpios de ejemplo.
La estrategia

Dos frentes en paralelo, no uno detrás de otro

La confusión habitual es creer que primero se hace TODA la estructura y después TODA la base de datos. En realidad son dos frentes que arrancan juntos, y solo la optimización de la DB espera a los dos.

🧱 Frente A — Estructura (código)
1

Análisis + Tests + Migración por módulo arranca ya

Cada módulo pasa por su ficha, se le escriben los tests que congelan lo que hace hoy, y se migra a Features/ limpio. Se avanza tier por tier: los 21 simples primero.

2

El sistema no se apaga nunca

El módulo viejo y el nuevo conviven. Se cambia cliente por cliente con un interruptor. Si algo falla, se vuelve atrás al instante.

🗄️ Frente B — Base de datos
1

Versionar la base arranca ya, en paralelo

Ponerle control de versión al schema. No depende de tocar el código. Es el habilitador de todo lo que sigue.

2

Optimizar la base espera a A + B1

Índices, consultas lentas, mover SPs al ORM. Solo se hace cuando ya hay tests (para no romper) y versionado (para poder propagar el cambio a todos los clientes).

Regla que ordena todo: estructura y versionado corren juntos desde el día uno — ninguno depende del otro. La optimización de la base espera a tener tests y versionado. El ORM no es una fase: ya existe (EF Core), se consolida de a poco dentro de cada módulo.
El mecanismo que no se veía

¿Cómo refactorizamos sin tocar el código viejo?

El punto delicado

Versionar la base: qué tan fuerte es

Es el cuello de botella más crítico de todo el plan. No por dificultad técnica, sino porque el sistema tiene una base de datos por cada cliente.

⛓️ Multiplicación

Hay 1 base por suscripción. Cada cambio de schema hay que aplicarlo a la base central y a cada cliente. Con 50 clientes, un solo cambio son 51 aplicaciones. A mano es inviable.

🌫️ Divergencia oculta

Como hoy el schema se toca a mano, no hay garantía de que todas las bases sean iguales. Pueden haber divergido y nadie lo sabe hasta que un cambio rompe solo en un cliente.

🧩 Los SPs cuentan

Los 21 procedimientos con lógica de negocio también son parte del schema y también hay que versionarlos, no solo las tablas.

✗ NO: usar migraciones del ORM como dueño del schema

  • El schema ya existe y no lo creó el ORM.
  • Son ~220 tablas + 21 SPs + vistas: forzar al ORM a "adoptarlos" es frágil.
  • Las migraciones del ORM manejan mal los procedimientos almacenados.

✓ SÍ: scripts SQL numerados + un ejecutor (DbUp)

  • Cada cambio = un script versionado (V007__agrega_indice.sql).
  • El ejecutor lleva la cuenta en cada base y aplica solo lo que falta.
  • Multi-cliente: recorre todas las bases con un comando y sabés qué versión tiene cada una.
  • El ORM (EF Core) sigue como acceso a datos. Conviven.
Lo difícil no es la herramienta (se monta en días). Es el arranque —crear la línea base y auditar la divergencia entre clientes— y sobre todo la disciplina: desde ese día, nadie vuelve a tocar el schema a mano. Todo pasa por un script versionado. Esa regla es el 80% del valor.
⚠️ Dato que todavía falta y define el riesgo real: cuántas bases de clientes hay hoy y si divergieron. Eso no está en el repositorio, está en el servidor SQL. El primer paso concreto de este frente es un script que compare el schema de cada cliente contra el central y muestre dónde difieren.

Cómo probamos con base de datos real

Tests contra base dedicada: 3 niveles de aislamiento

Los tests corren contra una copia aislada de la base (_test), no contra producción. El truco es que un test que escribe no ensucie al siguiente. Se resuelve según lo que hace cada test:

Solo lee

Listar, ver por ID, consultas. No cambia nada → no necesita aislamiento. Comparten la base, reset una vez. Costo: casi cero.

Escribe (1 conexión)

Crear, editar, borrar con el ORM. Cada test abre una transacción y la deshace al terminar. La base vuelve sola. Costo: milisegundos.

Cruza conexiones / SP

Cuando interviene un SP que confirma por su cuenta. Ahí se restaura desde una copia limpia. Costo: ~9 segundos.

El nivel del medio —transacción que se deshace— es el que falta construir, y ContactAddresses es el caso ideal para estrenarlo (escribe con una sola conexión, sin SPs). Una vez hecho, queda de molde para todos los módulos que escriben.

Por dónde arrancamos

Con todo lo anterior, el arranque no es opinión: es el módulo más simple, medido, que además sirve para estrenar los dos patrones que faltan.

▶ Módulo piloto: ContactAddresses (TIER 1)

1 dependencia · 5 métodos · 16 tests derivados del código · aislado (no rompe a nadie). Estrena el patrón de transacción-que-se-deshace y deja el molde para los otros 20 módulos simples.

Frente A — arranca con esto

Ficha de ContactAddresses ✅ hecha → construir el fixture de escritura → 16 tests → registrar en el tablero. ~2-3 días. Luego el siguiente TIER 1.

Frente B — arranca con esto

Script de auditoría de divergencia entre las bases de clientes. Es lo primero que hay que saber antes de montar el versionado.

Estos dos frentes pueden empezar la misma semana, en paralelo. No se estorban. La optimización de la base queda para cuando ambos tengan avance.
