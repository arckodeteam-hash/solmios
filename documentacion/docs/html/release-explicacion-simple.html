🍽️ Release Branch Explicado como Restaurante

La Cocina de Kaptas ERP
👨‍🍳

main = El menú oficial que ven los clientes. Solo platos probados y en producción.

feature/* = Cada chef (DEV) prueba una receta nueva en su propia estación.

pre-produccion = La cocina central donde se juntan todas las recetas. Hay platos a medio hacer, experimentos, desorden.

release/vX.X.X = La bandeja del día. Se arma SOLO con platos que el chef ejecutivo ya aprobó. No se agregan ingredientes nuevos. Solo ajustar la presentación.

hotfix/* = Un cliente se quejó. El chef corrige sobre la marcha en la receta oficial (main).

📌 ¿Cuántas Ramas Existen en Total?

En cualquier momento del día, estas son las ramas que existen en el repositorio:

PERMANENTE main Producción — lo que usan los clientes → siempre existe
PERMANENTE pre-produccion Entorno de pruebas — WIP de todos → siempre existe
TEMPORAL feature/xxx Una por cada tarea nueva ← se crea desde main
TEMPORAL fix/xxx Una por cada bug no urgente ← se crea desde main
TEMPORAL refactor/xxx Para reestructurar código ← se crea desde main
TEMPORAL release/vX.X.X Solo se crea cuando hay que pasar a producción ← se crea desde main
TEMPORAL hotfix/xxx Bug crítico en producción ← se crea desde main
💡 Regla de oro: TODAS las ramas temporales se crean desde main

La ÚNICA excepción: si QA-UI encuentra un bug durante las pruebas de la release,
el fix se crea desde release/vX.X.X (porque el bug está ahí, no en main).

Release solo existe al final de la semana, cuando hay features listas para producción. El resto del tiempo NO HAY release branch. Es temporal.

🎯 ¿Qué Pasa Exactamente Cuando Se Crea release/vX.X.X?
1
Se crea desde main — Arranca con el código limpio de producción. No trae WIP de nadie, no trae basura.
2
Se mergean SOLO las features aprobadas (las que pasaron QA-DEV y QA-UI). Nada más. No se aceptan features nuevas aquí.
3
QA-UI prueba TODO junto — Feature A + Feature B + Feature C. Si algo se rompe, el bug está AQUÍ en la release.
4
Bug en QA-UI → fix desde release — Creas fix/boton-roto desde release/v2.1.0, corriges, PR a release, QA-DEV aprueba, merge.
5
Release → main — Cuando QA-UI dice "OK", José/Ricardo mergean release a main. Se taggea la versión. A producción.
6
Se borra release — Ya cumplió su propósito. La rama desaparece.

🍝 El Mismo Problema en un Restaurante
👨‍🍳

El menú oficial (main) tiene 5 platos. El chef crea 2 platos nuevos (Feature Login, Feature Reportes). El chef ejecutivo los prueba y dice "están buenos, salen la próxima semana".

Jueves: arman la bandeja release con los 5 platos oficiales + los 2 nuevos.

El mesero prueba la bandeja y dice: "El plato nuevo 1 mancha el plato nuevo 2" (bug de integración).

¿Dónde corriges?
❌ ¿En el menú oficial (main)? No, porque ahí los platos nuevos NO existen.
✅ En la bandeja release, que es donde están los 2 platos nuevos juntos.
Corriges la presentación ahí, vuelves a probar, y cuando está bien → se sirve al cliente (main).
