🛡️ Estrategia Anti-Conflictos: Cómo NO heredar errores de otros

❌ Error común
pre-produccion (tiene Bug A + WIP B)
  └── feature/mia
      → Me llevo Bug A sin saberlo
      → PR tiene errores que no son míos
      → QA-DEV rechaza por código ajeno
✅ Solución: ramas desde main
main (código limpio, solo aprobado)
  └── feature/mia
      → Solo mi código, cero ruido
      → PR contiene solo mis cambios
      → QA-DEV revisa solo mi lógica
📋 Reglas para evitar conflictos
1. Rama siempre desde main
git checkout main && git pull
→ git checkout -b feature/xxx
2. PR pequeño y frecuente
Menos de 400 líneas por PR.
Si es más grande, dividir en 2+ PRs.
3. Merge a pre-produccion solo aprobado
Ricardo mergea SOLO después de
aprobación de QA-DEV.
4. Release desde main
release/vX.X.X se crea desde
main, no desde pre-produccion.
5. Rebase antes del PR
Antes de abrir PR: git rebase main
para resolver conflictos localmente.
6. Nadie mergea su propio PR
El que codea no revisa. El que revisa
no codea. Siempre otro par de ojos.
⚠️ ¿Qué hacer si hay conflictos en el PR?
1. No resolver conflictos por la web de GitHub — siempre localmente.
2. git checkout main && git pull → git checkout feature/mia → git rebase main
3. Resolver conflictos uno por uno con git mergetool o manualmente.
4. git push --force-with-lease (solo si trabajas solo en tu rama).
5. Si el conflicto es muy grande (10+ archivos), crear nueva rama desde main y re-aplicar cambios manualmente.

🛡️ Estrategia: Ramas desde main = cero contaminación cruzada

❌ ANTES (desde pre-produccion)
pre-produccion → [Bug A] [WIP B] [Fix C]
    └── feature/mia → 😱 me llevo Bug A + WIP B
        → PR rechazado por errores que no son míos
✅ AHORA (desde main)
main → [Código limpio y aprobado]
    └── feature/mia → ✅ solo mi código
        → PR solo con mis cambios, sin ruido
Tipo Desde qué rama Cuándo crearla Comando
✨ Feature main • Nueva funcionalidad solicitada
• Nuevo módulo del ERP
• Cuando el Arquitecto asigna una tarea nueva del backlog 		git checkout main
git pull
git checkout -b feature/nombre-tarea
🔧 Fix main • Bug encontrado en desarrollo
• Bug encontrado en QA-UI
• Error que NO bloquea producción
• Cuando Joel o José rechazan y piden corrección menor 		git checkout main
git pull
git checkout -b fix/nombre-fix
🚨 Hotfix main • Bug CRÍTICO en producción
• Sistema caído o bloqueado
• Error que afecta a usuarios finales
• URGENTE - requiere deploy inmediato 		git checkout main
git pull
git checkout -b hotfix/nombre-hotfix
♻️ Refactor main • Mejorar código existente
• Optimizar performance
• Reestructurar módulo
• Sin cambiar funcionalidad 		git checkout main
git pull
git checkout -b refactor/nombre-modulo

⚠️ REGLA DE ORO — Aislamiento de Ramas

TODAS las ramas se crean desde main (incluyendo feature, fix y refactor).

¿Por qué desde main y no desde pre-produccion?
pre-produccion contiene código de TODOS los DEV en pruebas — bugs, WIP, features sin terminar. Si creas tu rama desde ahí, te llevas los errores de otros sin saberlo.

main solo tiene código aprobado y en producción — base limpia garantizada.

NUNCA crear ramas desde ramas de features anteriores.

SIEMPRE hacer git checkout main && git pull ANTES de crear una nueva rama.
