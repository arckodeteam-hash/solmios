🧪 Qué hay que probar (de verdad, no genérico)

1 · Caracterización (foto del viejo) — capturar el JSON que el legado devuelve HOY para cada endpoint, y usarlo de referencia. Es el "golden master".

2 · Comparación byte a byte (viejo vs v2) — por cada endpoint, pegarle a los dos por HTTP con el mismo input y exigir el mismo JSON exacto. Es el juez, igual que en Taller.

3 · Verificación input → output por endpoint (lo concreto):

4 · Seguridad (IDOR) — por cada método por-Id, pedir un contacto de otra empresa y exigir que el v2 rechace (401), donde el viejo devolvía datos ajenos.

5 · Escrituras con datos descartables — Create/Update/Delete modifican la base: usar contactos throwaway y resetear la base entre corridas (ya lo tenemos montado).

⚠️ Lo que puede complicar los tests (leer antes de estimar)

1 · GetRncData pega a un tercero (api.indexa.do). No se puede comparar byte a byte contra una API externa que se puede caer, cambiar o pedir token. Hay que simular (mock) esa llamada en los tests. Además hoy la URL está fija en el código, sin credencial ni timeout, y falla en silencio — se corrige de paso.
2 · GetClientesAdministrados devuelve métricas que dependen de la fecha. "Ventas últimos 3 meses", "última venta", "total por cobrar" cambian con el tiempo. Un golden master byte a byte se rompe mañana. Hay que fijar una fecha de referencia o tolerar esos campos en la comparación.
3 · Al cerrar el IDOR, el v2 NO será idéntico al viejo en los casos cross-tenant — y está bien. El viejo devuelve datos de otra empresa; el v2 devuelve 401. Es una diferencia intencional (mejora de seguridad), igual que en Taller. El test debe esperar esa diferencia, no marcarla como error.
4 · Create y Update hoy son asimétricos. El alta usa un procedure con 4 listas; la edición (por EF) no toca números ni precios e itera una colección mal recargada. Decisión a tomar: replicar el bug tal cual primero (para que el test pase idéntico) y corregirlo después con su propio test. No "arreglar de paso".
5 · NO mover el namespace Kaptas.DTOs.Contact. Ahí vive PaginationDTO, del que heredan 45 DTOs de todo el ERP (bancos, facturas, nómina, productos…). Migrar los DTOs de contacto a propios es seguro, pero tocar esa carpeta/namespace rompe medio sistema.

🔗 Qué afecta (impacto)

Migrar el servicio es seguro. Solo el ContactController usa IContactService; ningún otro módulo lo inyecta. Cambiar la clase no rompe a nadie más.
Lo que NO se puede tocar es la tabla Contactos ni sus procedures. Media docena de módulos (Ventas, Compras, Gastos, Notas de Crédito, Caja, Restaurante, Empleados, el propio Taller) leen esa tabla directo por SQL. Se reescribe el acceso en C#, pero el esquema y los SP se dejan intactos — igual que con Taller.

Este cronograma sale del análisis real del código y la base de prueba (21 endpoints mapeados uno por uno). Las estimaciones son rangos, no promesas: el comodín es GetRncData (si el tercero pide token/tiene rate-limit, suma medio día).
