🧠 Mapa mental — por qué esta opción

Del problema a la decisión. El nodo central es la meta; las ramas son las 3 alternativas que evaluamos.

Tests reproducibles y aislados para todo el equipo
▼

🐳 A · Docker + .bak compartido

  • Cada uno levanta SQL Server local
  • Restaura un .bak desde storage
  • ✗ El .bak pesa y hay que mantenerlo
  • ✗ No es "como Laravel"

📦 B · Schema versionado + Testcontainers

  • Extraer schema a .sql y versionarlo
  • Tests levantan su propio SQL Server
  • ✗ Drift MANUAL: mantener los .sql al día
  • ✗ Setup complejo, arranque lento

🌐 C · Server online de prueba ELEGIDA

  • Apuntar tests al server 173.249.31.75
  • Schema vive ahí (lo mantiene el DBA)
  • ✓ Reutiliza TODO lo armado
  • ✓ Cero drift manual
  • ✓ Compañeros: solo cambian 1 variable

BDs _test dedicadas

Lo clave: las BD reales (kaptaswebdev / kw21) nunca se tocan. Los tests trabajan sobre copias _test que se resetean solas antes de cada corrida.

⚙️ Qué pasa cuando hacés dotnet test

1
MSBuild ejecuta setup-test-db.sh --reset-only antes de que arranquen los tests.
2
El script hace RESTORE de las BDs _test desde un snapshot limpio → quedan vírgenes (2 segundos).
3
xUnit corre los 239 tests apuntando a las BDs _test.
4
Las BDs dev ni se enteraron. Cero contaminación.

🧩 Los 2 tipos de test

UNITARIOS

Features/ — sin BD

  • ⚡ ~1 segundo · 43 tests
  • Lógica pura con mocks (crypto, cálculos, validaciones)
  • andan en cualquier CI sin nada
INTEGRATION

Legacy/ — contra BD _test

  • 🐢 ~45 segundos · 196 tests
  • Queries, SPs y datos reales aislados
  • necesitan la BD _test

👥 Cómo lo usa cada rol

💻 Vos (local)

bash setup-test-db.sh   # 1ª vez
dotnet test

Docker local, rápido (~1ms por query).

👤 Compañero nuevo

git clone ...
# setea la credencial del server
dotnet test

Apunta al server online, sin instalar Docker SQL.

🤖 CI / GitLab

build
setup-test-db.sh --reset-only
dotnet test

Autónomo, credenciales por secret.

🛟 Los 3 cuidados de la Opción C

Credenciales

Nunca en el repo

Host y password van por variables de entorno / secrets de GitLab. El repo queda limpio.

Drift

Sync con prod

Job nocturno que restaura el server de prueba desde prod → nunca se queda "lejos de lo actual".

Contención

BD por persona

Cada dev/CI usa su BD _test (kw21_test_joel, etc.) para no pisarse.
