🌿 Git Workflows: Lo Que Usan las Grandes Empresas

Git Flow, GitHub Flow, GitLab Flow, Release Flow — y cuál elegir para Kaptas ERP

Basado en Atlassian, GitLab, Microsoft, Netflix, Spotify

📚 Los 4 Workflows que Usan las Grandes Empresas

🏗️ Git Flow

Usado por: Atlassian, Microsoft (legado), WordPress

El más estructurado. Creado por Vincent Driessen en 2010. Tiene ramas main, develop, feature/*, release/*, hotfix/*.

  • Control total de releases
  • Soporte para múltiples versiones simultáneas
  • Claro para equipos grandes
  • Complejo — mucha sobrecarga de ramas
  • Lento — bloquea features esperando release
  • Obsoleto para CI/CD moderno

    • ⚡ GitHub Flow

    Usado por: GitHub, Netflix, Shopify

    Simple: solo main + ramas feature. Todo se mergea a main y se deploya. Ideal para despliegue continuo.

  • Muy simple — fácil de aprender
  • Ideal para deploy múltiples veces al día
  • Sin sobrecarga de ramas
  • Sin staging environment definido
  • No sirve para releases programadas
  • Peligroso si no tienes CI/CD sólido

    • 🔄 GitLab Flow

    Usado por: GitLab, DigitalOcean

    Híbrido: features desde main, promoción por entornos (staging → production). Ramas de entorno persistentes.

  • Balance entre estructura y simplicidad
  • Entornos bien definidos
  • Integración nativa con CI/CD
  • Puede tener ramas largas
  • No maneja bien múltiples versiones

    • 🎯 Release Flow

    Usado por: Microsoft (moderno), Azure DevOps

    Evolución de Git Flow simplificado. Features desde main, release/* para estabilización, bugfix/* desde release. El más recomendado para Kaptas.

  • Features desde main → aislamiento total
  • Release branches para estabilización
  • Bugfix desde release → coincides con el bug exacto
  • Release → main solo cuando está probado
  • Requiere disciplina en merges
  • Más ramas que GitHub Flow

    • 🎯 ¿Por Qué Usar release/vX.X.X?

    🧠 El problema que resuelve release

    Imagina: 3 DEV trabajando en paralelo. DEV 01 termina "Feature A", DEV 02 termina "Feature B". QA-UI empieza a probar y encuentra un bug en Feature B.

    ¿Dónde está el bug? En Feature B, que está en pre-produccion mezclada con Feature A.
    ¿Desde dónde creas el fix?

    ❌ Desde main: El bug NO existe en main porque Feature B nunca se ha desplegado. Codeas a ciegas.
    ✅ Desde release/vX.X.X: La release contiene EXACTAMENTE Feature A + Feature B. Puedes reproducir el bug y corregirlo.

    ✅ Por qué release NO es lo mismo que pre-produccion

    pre-produccion → WIP de todos los DEV, features a medio hacer, bugs sin corregir, código inestable.
    release/vX.X.X → Solo features APROBADAS por QA-DEV, validadas, listas para producción.

    Cuando creas un fix desde release/vX.X.X, estás trabajando sobre código que YA FUE APROBADO y que ESTÁ DESTINADO A PRODUCCIÓN. No estás heredando basura de nadie.

    Tabla Decisoria: ¿Desde dónde creo mi rama?

    Escenario Rama base ¿Por qué?
    ✨ Feature nueva main Base limpia, sin código de otros
    ♻️ Refactor main Se hace sobre código en producción
    🔧 Bug en desarrollo local misma feature branch No necesitas nueva rama, corriges y push
    🔧 Bug encontrado en QA-DEV (PR) misma feature branch Corriges en tu rama, el PR se actualiza solo
    🔧 Bug encontrado en QA-UI (pruebas) release/vX.X.X El bug está en una feature de este release. Desde main no existe el bug.
    🚨 Hotfix (producción caída) main Urgente, el bug está en producción

    ✅ Flujo Recomendado para Kaptas ERP

    ✨ Feature / Refactor

    main (limpio)
    └── feature/mi-tarea
        PR → qa
        QA-DEV aprueba ✅
        Merge a pre-produccion
        QA-UI prueba
        Pasa → entra en release/vX.X.X

    🔧 Bug en QA-UI

    release/v1.2.0 (contiene el bug)
    └── fix/bug-en-B
        PR → qa
        QA-DEV aprueba ✅
        Merge a release/v1.2.0
        QA-UI prueba el fix
        Pasa → release → main

    🚨 Hotfix en producción

    main (bug en vivo)
    └── hotfix/urgencia
        PR → qa
        QA-DEV aprueba ✅
        Merge a main + pre-produccion
        Deploy inmediato

    📊 Diagrama de Flujo Completo

    main (código en producción, siempre estable)
    │
    feature/mi-tarea (desde main)
    │
    PR → qa (QA-DEV revisa)
    │
    pre-produccion (entorno de pruebas)
    │
    release/vX.X.X (desde main, features validadas)
    │
    fix/bug-en-release (desde release — el bug existe aquí)
    │
    release + fix merged (listo para producción)
    │
    main ← release/vX.X.X (producción actualizada)

    📋 Reglas Finales

    1. Features desde main

    Nunca desde pre-produccion. Garantiza que no heredas WIP de otros.

    2. Fix en pruebas desde release

    El bug está en la release. Desde main no existe. Desde release sí puedes reproducirlo.

    3. Release se crea desde main

    Solo features aprobadas. Release candidate limpio y controlado.

    4. Hotfix desde main

    Urgente. El bug está en producción. Fix directo a main + retro a pre-produccion.

    5. Fix mergea a release, no a pre-produccion

    El fix se integra directo a la release, no ensucia pre-produccion con merges extraños.

    6. Release mergea a main

    Cuando release está estable y QA-UI aprueba → merge a main = producción.

    💡 Conclusión: La Confusión "main vs release"

    Tu intuición era correcta desde el principio:

    Cuando te dije "todo desde main", estaba bien para features nuevas. Pero para bugs encontrados en pruebas, crear desde release/vX.X.X es lo correcto y lo que hacen las empresas que manejan releases programadas (Microsoft, Atlassian, GitLab).

    ¿Por qué no es lo mismo que crear desde main?
    Porque main en este momento NO tiene el bug. Si creas desde main, estás codeando sobre código que no se parece al entorno de pruebas. El fix no va a funcionar porque los archivos que necesitas tocar ni siquiera están en tu base.

    ✅ Fix desde release = código exacto del bug + fix preciso + merge ordenado a main.
