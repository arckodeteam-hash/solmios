2 · Con qué está conectado (y para qué)

Pieza del móduloSe conecta aPara qué
ICurrentUserProviderkaptaswebdev kw21 + headers/JWTSaber quién es el usuario y en qué empresa opera; validar que la empresa sea suya
ITenantConnectionFactorykaptaswebdev (suscripción → base) + cachéResolver a qué base del tenant conectarse; se cachea 8 h
ISpRunnerkw21 vía DapperEjecutar los stored procedures del taller
IUserBranchesQuerykw21 (Users_Company, Branches, Stores)Traer las sucursales del usuario para la pantalla inicial
Los 9 SPsSPs anidados + tablasToda la lógica: cálculos, validaciones, facturación fiscal
DTOs compartidosKaptas.DTO (monedas, pagos, sucursales)Tipos de otros dominios que se reusan (la guía lo permite)
Dos bases, no una: kaptaswebdev es la base "central" (usuarios, permisos, suscripciones, y a qué base va cada cliente). kw21 es la base del tenant (los datos reales del taller de ese cliente). El módulo toca las dos.

Lee de

Casos de taller, contactos, monedas, productos, técnicos, tipos de comprobante, sucursales, y la config de la empresa.

Escribe en

Operacion, Operacion_taller, Operacion_det_taller al crear/editar casos. Al facturar (Complete) además emite un comprobante fiscal y consume una secuencia NCF de CONTROL_NCF — eso es dinero y es fiscal.

Lo delicado: la facturación (P_Taller_Finalizar_Grabar) toca el flujo fiscal electrónico (NCF, DGII). Un error ahí no es un bug, es un problema con Hacienda. Por eso es el último candidato a tocar.

4 · Cómo mejorar el módulo (para mejorar el sistema)

Ordenado de menor a mayor riesgo. Cada paso se valida contra los tests de comparación byte a byte que ya existen.

  1. Migrar los SPs de lectura a C# riesgo bajo
    Get_By_id, Casos_Paging, datos_iniciales, Print son queries. Reescribirlas en LINQ hace al módulo independiente de esos SPs. El test confirma que dan idéntico. Esto es lo que de verdad "quita" SPs.
  2. Replicar el ValidateTenantFilter a los demás módulos riesgo bajo
    El D2 (empresa sin validar) es un agujero de todo el sistema, no solo del taller. El patrón que ya funciona acá cierra el IDOR en cualquier módulo nuevo.
  3. Arreglar el log de errores ('ADMIN' fijo) riesgo bajo
    Los SPs registran los errores como "ADMIN". Pasar el usuario real hace el log útil para rastrear qué pasó y quién.
  4. Versionar los SPs anidados riesgo medio
    p_taller_product_insert_upd, p_Taller_Finalizar, P_Ncf_Get_Set, usp_log_error son la cadena de lógica. Ponerlos en git (como ya hicimos con los 9) da la foto completa.
  5. Migrar las escrituras de edición a C# riesgo medio
    ChangeStatus, UpdateHeading son UPDATEs con validación. Migrables, con la red de tests.
  6. La facturación (Finalizar) — evaluar, no apurar riesgo alto
    Emite NCF electrónico. Reescribir esto en C# es un proyecto en sí y de altísimo riesgo. Recomendación: dejarlo encapsulado (documentado, versionado) hasta que el negocio decida que vale la pena. No todo lo que se puede migrar conviene migrarlo.
El principio que hace todo esto seguro: nunca se migra a ciegas. Cada SP que se pasa a C# se valida contra el test de comparación byte a byte (v2 = legado). Si el C# devuelve un centavo distinto, el test falla y te enterás antes de producción.
